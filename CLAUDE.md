This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## О проекте

Конвейер извлечения данных для белорусских судебных/третейских документов: на вход
приходят документы (договор займа, исковое заявление, претензия, свидетельство СОЗ,
`vvod_dannyh.txt` и т.п.), на выходе — JSON-карта `{{PLACEHOLDER}}: значение`, по
которой `documents.py` заполняет docx-шаблоны.

**Текущее состояние:** конвейер реализован на чистом Python (без n8n). **Все значения
извлекаются детерминированно кодом (regex/правила) — LLM не используется.** Это возможно,
потому что входные документы — машинно-сгенерированные шаблоны сервиса «Капуста» с
устойчивыми подписями полей и форматами дат/чисел. Ядро — `pipeline.py`.

`n8n.json` сохранён как историческая справка об исходном воркфлоу; для запуска он не
нужен. Ранняя версия порта вызывала YandexGPT — она удалена (вместе с `prompt_data.py`,
маскированием ПДн, расчётом стоимости, зависимостью `requests`).

## Архитектура (порядок выполнения в `pipeline.py: run_pipeline()`)

1. **`read_source_texts` / `combine_texts`** — читает `out_txt/*.txt`, склеивает в один
   текст с заголовками `==== имя_файла ====`. DOCX/TXT в текст конвертирует заранее
   `uploading_documents.py`.
2. **`normalize_combined`** — нормализация (склейка переносов, выделение разделов).
3. **`extract_vvod_dannyh`** — парсит `vvod_dannyh.txt` (генерируется `data_entry.py`)
   построчно «Метка: значение»: город, судья, суд, номера/даты, реквизиты заседания.
4. **`extract_documents`** — по фиксированным фразам шаблонов тянет: ФИО сторон (для
   склонений), номер/дата/срок/ставку займа, первую строку графика платежей, суммы из
   искового (осн. долг, проценты, неустойка). Суммы берутся из **искового** (слово
   «искового заявления» отсекает аналогичные фразы претензии). Извлекаются ТОЛЬКО поля,
   реально подставляемые в итоговые docx; неиспользуемые (email, ИНН, паспорт, способ
   погашения и т.п.) намеренно не ищутся.
5. **`_apply_normalizers`** — приводит ФИО/адреса/паспорта к каноническому регистру
   (`normalize_name`, `normalize_address`, `normalize_passport`).
6. **`extract_from_certificate`** — из Свидетельства СОЗ: адреса сторон, `LOANDATE_START`,
   `LOAN_AMOUNT`. Перекрывает значения из шага 4.
7. **`extract_strict_markers`** — `PRETENSION_DATE`, `PENALTY_TO` (период пеней по контексту).
8. **`fix_address_casing`** — лейблы адресов в нижний регистр («Место Регистрации:» →
   «место регистрации:», «Агрогородок» → «агрогородок» и т.п.).
9. **`compute_formulas`** — производные: `PRINCIPAL_SUM` (формат BYN), `TOTAL_SUM`,
   `INTEREST_FROM/TO`, `PENALTY_FROM` (`LOANDATE_END`+1),
   `JUDGE_INITIALS`, `JUDGE_POSITION_WITH_DASH`, префикс `CITY`.
10. **`save_out_json`** — пишет словарь `{{KEY}}: value` в `out_txt/out_txt.json`.

Дальше (вне `pipeline.py`): `morph_fio.py` дописывает склонённые ФИО, `documents.py`
подставляет плейсхолдеры в docx. Поле, не найденное регуляркой, просто не попадает в
результат — прогон не падает (`documents.py` подставит пробел).

## Важные детали

- **Экстракторы заточены под шаблоны сервиса «Капуста»** — устойчивые подписи полей и
  формат дат `DD.MM.YYYY`. Регексы привязаны к содержимому (не к именам файлов) и терпимы
  к пробелам/переносам, т.к. раскладка txt зависит от конвертера. Документы другой
  структуры потребуют доработки регулярок.
- **Результат — словарь `{{KEY}}: value`** в `out_txt/out_txt.json`. Имена ключей фиксированы
  в экстракторах; формульные ключи вычисляет `compute_formulas()`. Схема имён —
  `PLAINTIFF_*` / `DEFENDANT_*` / `JUDGE_FULL` и т.д. (бывшая несогласованность с
  `LOAN_NUMBER`/`CLAIMANT_*` из старого n8n снята).
- **Приоритет источника:** при расхождении сумм между претензией и исковым берётся исковое
  (якорь по слову «искового заявления»); адреса/дата/сумма займа из Свидетельства СОЗ
  перекрывают значения из остальных документов.
- DOCX читается без сторонних библиотек намеренно (в `uploading_documents.py`) — сохраняйте
  подход, если нет явного запроса добавить зависимость.
- Пошаговый лог прогона — в `runs.jsonl`; диагностический снимок склеенного входа —
  `last_input.txt`.

## Рекомендации по поведению

**Не делайте предположений. Не скрывайте непонимание. Выявляйте компромиссы.**

- Перед реализацией чётко сформулируйте предположения; при нескольких интерпретациях
  представьте их, не выбирайте молча; если непонятно — остановитесь и спросите.
- **Простота прежде всего:** минимальный код, решающий задачу. Никаких функций сверх
  запрошенного, абстракций для одноразового кода, неоправданной «гибкости». Если 200
  строк можно заменить на 50 — перепишите.
- **Хирургические изменения:** меняйте только необходимое, придерживайтесь
  существующего стиля, не рефакторьте рабочий код. Удаляйте только тот «мусор», который
  создали ваши же правки; чужой мёртвый код не трогайте — упомяните о нём.
- **Целенаправленное выполнение:** превращайте задачи в проверяемые цели (баг → тест,
  воспроизводящий баг → зелёный тест). Для многоэтапных задач — краткий план с
  критериями проверки на каждом шаге.
